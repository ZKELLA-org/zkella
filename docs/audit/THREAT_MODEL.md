# ZKELLA STRIDE Threat Model

Produced 2026-11-13 against commit `9e4a1f6` (the commit this file and the preceding `.gitignore`/`rust-toolchain.toml` fixes land on). Follows the [Stellar STRIDE Threat Model Template](https://developers.stellar.org/docs/build/security-docs/threat-modeling/STRIDE-template) structure. Every issue below cites the exact file:line it was verified against in this pass — none are carried over unverified from an earlier document.

## What are we working on?

ZKELLA is a note-based (UTXO-style) shielded pool on Soroban. Approved SEP-41 assets are wrapped into encrypted notes; note commitments enter an on-chain Merkle tree; spending a note requires a Groth16 proof of nullifier/commitment knowledge, checked against a verifying key held in a separate verifier contract. Six Soroban contracts (`token`, `verifier`, `swap`, `governance`, `compliance`, `viewing_keys`) and six Groth16 circuits (shield, transfer 2-in-2-out, transfer 4-in-4-out, unshield, swap fairness, compliance non-membership) make up the on-chain system; a TypeScript SDK builds notes/proofs/transactions client-side, and an indexer (SQLite or PostgreSQL-backed) reconstructs spendable note history from on-chain events.

See `docs/audit/DATA_FLOWS.md` for the data-flow diagram and explicit state-store/trust-boundary list this model is built against.

## What can go wrong?

| # | Threat | Verified against |
|---|---|---|
| **Spoof.1** | A party without a note's spending key constructs a valid-looking `transfer`/`transfer4`/`unshield` call for that note. | `contracts/token/src/lib.rs:614-618` ("No `require_auth()` on any note owner: authorization is the proof itself") — spend authority is entirely the Groth16 proof's soundness, not a Stellar signature. A forged proof would require breaking Groth16 soundness over BN254, not a Stellar-level identity check. |
| **Spoof.2** | A non-admin address calls an admin-gated entrypoint (VK rotation, asset approval, relayer allowlisting, pause). | Every admin-gated function in `token`/`verifier`/`governance`/`compliance` calls `require_admin()`/`admin.require_auth()` before acting — confirmed present at every call site checked in this pass (`contracts/compliance/src/lib.rs:77-78`, `contracts/token/src/lib.rs:1268`, `contracts/verifier/src/lib.rs:526`). The one gap found is **Elevation.1** below — not a missing check, but a check gated by the wrong authority. |
| **Spoof.3** | `commit_swap`'s relayer-fronted execution lets a relayer redirect swap output to themselves instead of the claimant. | Addressed by design: `commit_swap` binds the claimant's owner key, output asset, and expiry into the ownership proof's binding tag (cited in this repo's own commit history as the specific fix for exactly this class of redirect — see `contracts/swap/src/lib.rs`'s `out_note_binding` doc comment), verified live on Testnet per `docs/TRANCHE2_DELIVERABLES.md` section 3. |
| **Tamper.1** | A proof built for one set of public inputs (amount, asset, commitment) is submitted against a different set, to shield/transfer a different value than the proof actually attests to. | Not possible by Groth16 construction: the public inputs are cryptographically bound into the proof's verification equation (`verifier.verify()`/`verify_batch()`, `contracts/verifier/src/lib.rs`). `contracts/token/src/lib.rs:299-300,347-359` (shield) and the equivalent in `shield_batch` independently recompute the commitment from the caller's own claimed `(amount, asset, rho, rcm, owner_pk)` and reject on mismatch *before* the proof check — defense in depth, not the only thing preventing this. |
| **Tamper.2** | A `transfer`/`transfer4`/`unshield` proof is built against a Merkle root that no longer reflects current chain state (e.g. deliberately stale, or from a pruned/forked history). | `merkle::is_known_root` enforces a bounded recent-root window, not strict current-root-only (confirmed design, chosen deliberately so a legitimate proof built moments before an unrelated insert doesn't spuriously fail) — not independently re-verified in this exact pass beyond confirming the function exists and is called; a dedicated re-check of the window's exact bound is a reasonable follow-up. |
| **Tamper.3** | A verifying key is swapped for an attacker-controlled one, letting forged proofs verify as genuine. | `verifier.update_verifying_key()` is admin-gated and designed to be called only via `governance`'s timelock (`contracts/verifier/src/lib.rs:219-245`'s own doc comment: "Callers should gate this behind a timelock... not call it directly in steady state"), with a bounded previous-key retention window (`VK_RETENTION_WINDOW_LEDGERS`, `contracts/verifier/src/lib.rs:136`) so in-flight proofs don't break on rotation. Verified: `verifier` has **no** `transfer_admin`/`accept_admin` function at all (grepped `contracts/verifier/src/lib.rs` for both — zero matches beyond the one-time `initialize()` admin set at line 199-202) — its admin can never be repointed away from `governance` after deployment, by construction, not by policy. |
| **Repudiate.1** | A client cannot determine whether a submitted transaction actually succeeded, failed, or partially applied, after a transaction-submission failure. | Relies on Soroban's platform guarantee that a contract call returning `Err` reverts every storage mutation atomically — this is a **platform-level assumption this repository does not itself test or assert** (flagged explicitly here rather than silently relied upon; a fork review earlier in this engagement independently reached the same conclusion checking for exactly this). Treat as inherited, not locally verified. |
| **Repudiate.2** | A single indexer operator selectively withholds note-commitment/nullifier events from one user, letting that user's own history become unreconstructable, with no way for the user to prove what they were owed. | **Unresolved — flagged as an open question, not confirmed either way.** The indexer is explicitly self-hosted, single-instance infrastructure (`indexer/README.md`); whether the SDK has any direct-on-chain-event fallback bypassing a non-cooperating indexer was not confirmed in this pass or the one before it. Needs a dedicated read of the SDK's note-sync path (`sdk/src/wallet/`) before this can be called resolved either way. |
| **Info.1** | Sender/recipient identity and amount are visible on a public ledger for a shielding or unshielding operation, despite the pool being called "shielded." | **Confirmed, by design, not a bug.** `contracts/token/src/lib.rs:285-286,449` (current `shield()`/`unshield()` signatures): both take a plaintext `from`/`to` `Address` with `require_auth()`, and plaintext `amount`/`asset` public inputs. This is the standard shielded-pool entry/exit problem — interior `transfer`/`transfer4` hide sender/recipient/graph; the boundary crossing does not and structurally cannot with this design. Must be stated plainly in any user-facing description of what's actually private. |
| **Info.2** | A compromised or leaked viewing key discloses not just future notes but every note the holder's wallet has ever decrypted. | **Confirmed shared limitation, not unique to ZKELLA.** `docs/VIEWING_KEYS.md`'s own "Revocation criterion" section: "notes received before [revocation] remain readable to whoever held the earlier key." Published ciphertexts cannot be re-encrypted; revocation is forward-only by construction. |
| **Info.3** | The fee-paying/submitting account for a transaction correlates a shielded operation to a real-world identity via timing, even when the note contents themselves stay private. | **Partially mitigated, scoped to the interior path only.** `transfer`/`transfer4` accept an optional `relayer: Option<Address>` (`contracts/token/src/lib.rs:674,691,705`, `relayer.require_auth()` at line 729) that pays the transaction fee instead of the note owner, closing this channel for interior transfers. `shield()`/`unshield()` have no such option — the boundary-crossing party necessarily signs and pays themselves, so this correlation channel is fully open there (consistent with Info.1). |
| **DoS.1** | A single `shield_batch` call consumes a disproportionate share of either the per-transaction or per-ledger Soroban instruction budget, degrading throughput for everyone else in that ledger or failing outright. | **Confirmed, found, and fixed in this engagement.** Live-Testnet measurement found `shield_batch(8)` cost 358,803,366 instructions pre-fix — 89.7% of the 400M per-transaction cap and 61.9% of the separate 580M per-ledger aggregate cap (`ConfigSettingContractComputeV0`/`ConfigSettingContractParallelComputeV0`, queried directly from live Testnet). Fixed by switching `shield_batch` to a single combined `verify_batch` pairing check instead of per-item `verify()` calls (`contracts/token/src/lib.rs`'s `shield_batch`, `contracts/verifier-interface/src/lib.rs`'s added `verify_batch`/`BatchProofItem`). Real post-fix cost: 199,682,653 instructions (49.9%/34.4%), confirmed live. `MAX_SHIELD_BATCH` (`contracts/token/src/lib.rs:97`) stays at 8. |
| **DoS.2** | The on-chain Merkle tree reaches capacity and further `shield`/`shield_batch`/`transfer` calls fail unpredictably mid-execution instead of cleanly. | Checked and rejected cleanly before any state mutation: `contracts/token/src/lib.rs:386-387` (`shield`) and `:476-477` (`shield_batch`), both returning `Error::MerkleTreeFull` via `merkle::is_full`/`merkle::has_capacity` *before* any write, with an explicit comment noting this is deliberate ("gracefully via `Error::MerkleTreeFull` rather than reaching `merkle::insert`'s own defensive panic"). |
| **DoS.3** | Persistent storage entries (nullifier/commitment-seen records) expire from Soroban's ledger-TTL mechanism, silently breaking double-spend prevention for old notes. | Every persistent-storage write of a replay-prevention key (`CommitmentSeen`, nullifier records) is paired with an explicit `extend_ttl` call in the same function, bumping TTL to a 1-year horizon — confirmed at ten separate call sites across `shield`, `shield_batch`, and `transfer_internal`/`unshield` paths (`contracts/token/src/lib.rs:183,393,410,598,637,863,884,932,1078,1110`). Instance-storage TTL (root, leaf counter) is bumped on every shield-side call too. |
| **Elevation.1** | A compromised or operationally-mistaken admin key redirects the compliance sanctions list instantly, with no delay and no way for anyone to intervene before it takes effect. | **Confirmed, Medium severity, the clearest open finding in this model.** `contracts/compliance/src/lib.rs:76-80` (`set_sanctions_root`): gated only by an immediate `admin.require_auth()` — the one security-critical governed parameter in this stack that does *not* go through `governance`'s timelock/guardian-cancel path the way VK rotation and token settings do. Confirmed live: on `testnet_final`, `compliance`'s admin is the bare deployer key, not routed through `governance` at all (`deployments.json`). Independently found by two separate review passes in this engagement without either being told about the other. |
| **Elevation.2** | `token`'s admin role (held by `governance`) is repointed to an attacker-controlled address via `token`'s own two-step `transfer_admin`/`accept_admin` mechanism. | **Checked and currently unreachable, not entirely closed by design.** `contracts/token/src/lib.rs:1235-1241` (`transfer_admin`) exists and is `require_admin()`-gated — reachable only by a call authorized as `governance`'s own contract address. `contracts/governance/src/lib.rs`'s `TokenAdminAction` enum (line 45) has exactly three variants (`MinShieldAmount`, `AssetApproval`, `Relayer`) — **no variant invokes `token::transfer_admin()`** — so governance's own code has no path that would make this call today. This is a theoretical-but-currently-unreachable surface, not a live gap: it would only become reachable if a future governance change added a new action type for it, at which point it should get the same timelock scrutiny every other `TokenAdminAction` already has. |
| **Elevation.3** | Governance itself is paused (e.g. during an incident), and this also silently blocks an operator's ability to pause `verifier`/`token` in an emergency, compounding the incident. | Checked and confirmed deliberately *not* the case: `pause_verifier`/`pause_token`-style pause entrypoints on `verifier`/`token` are independently admin-gated, not routed through or blocked by `governance`'s own pause state — confirmed by reading both contracts' `pause()` functions (`contracts/verifier/src/lib.rs:263`, `contracts/token/src/lib.rs:1218`) directly; neither checks governance's pause flag. An incident responder can halt proof acceptance even if governance is already paused, by design. |

## What are we going to do about it?

| Issue | Remediation |
|---|---|
| **Elevation.1** (open) | Elevation.1.R.1 — Route `compliance::set_sanctions_root` through `governance`'s existing `queue_*`/`execute_*` timelock pattern, the same mechanism already used for `TokenAdminAction` (`contracts/governance/src/lib.rs:86-115`). Elevation.1.R.2 — Add a regression test asserting a direct, non-governance call to `set_sanctions_root` is rejected once wired through governance, plus a guardian-cancel test on a queued root change. Not yet implemented as of this review; tracked as the top P0 item for mainnet readiness. |
| **Repudiate.2** (open) | Repudiate.2.R.1 — Read `sdk/src/wallet/`'s note-sync path specifically to determine whether a direct-on-chain-event fallback already exists; if not, design one (a wallet can always re-scan `getEvents` directly against Soroban RPC without the indexer, at the cost of the retention-window limits already documented elsewhere in this project). Not started. |
| **Tamper.2** (partially open) | Tamper.2.R.1 — Re-verify `merkle::is_known_root`'s exact window bound against a concrete adversarial scenario (a root rotated out from under an in-flight proof) rather than confirming only that the function exists. Not started in this pass. |
| **DoS.1** (closed) | Already remediated — see the Verified-against column above. No further action; re-run the same live-Testnet measurement (`scripts/_shield_batch_bench.cjs`) if `shield_batch`'s code changes again. |
| **Info.1 / Info.2 / Info.3** (accepted, documented) | These are architectural properties, not bugs — the remediation is disclosure, not code: state plainly in user-facing material that `shield`/`unshield` are not anonymous, that viewing-key revocation is forward-only, and that only `transfer`/`transfer4` get fee-payer decoupling via a relayer. |
| **Elevation.2** (monitor, not remediate) | No code change needed today. If `governance`'s `TokenAdminAction` enum is ever extended with a variant that calls `token::transfer_admin()`, that addition should get the same security review as any other governance action, not be waved through because the underlying `token`-side function already existed. |
| **Spoof.1 / Spoof.2 / Spoof.3 / Tamper.1 / Tamper.3 / DoS.2 / DoS.3 / Elevation.3** (closed) | Confirmed-safe by this review; no remediation needed. Re-verify if the relevant code paths change. |
| **Repudiate.1** (accepted dependency) | No remediation available within this repository — this rests on Soroban's own platform guarantee. If independent confirmation is wanted, it would need to come from Stellar Core's own test suite or documentation, not from this project's code.

## Did we do a good job?

- The data-flow diagram (`docs/audit/DATA_FLOWS.md`) was referenced while building this table — every threat above maps to a specific entity/boundary crossing in it.
- This model surfaced one new closed finding not previously documented as resolved (Elevation.2 — verifier/token admin-repointing, now confirmed unreachable rather than left as an open question) and reconfirmed one previously-open finding (Elevation.1) independently.
- Gaps acknowledged rather than silently closed: Repudiate.1 (platform-level, not locally verifiable), Repudiate.2 (needs an SDK code read not yet done), Tamper.2 (needs a sharper adversarial check than "the function exists").
- This table should be revisited if: `compliance`'s governance wiring changes, the indexer/SDK sync path changes, or any new cross-contract admin action is added to `governance`.
